# Monitoring, improved and re-tested (Phase 7b)

Generated by `python -m pipeline.report_phase7b`; do not edit by hand. Independent checks: `python -m pipeline.verify_phase7b`. Walkthrough: `notebooks/07b_monitoring.ipynb`. Phase 7: `docs/MONITORING.md`.

**Why:** Phase 7's drift test raised false alarms in 11.6% of clean test runs (target 5%), because it compared sensor readings with training engines of the same age, not the same wear. Phase 7b replaces it and re-tests it on data nobody had seen: NASA's FD002 and FD004 (six operating conditions; FD004 also has two fault modes).

**Order of work (each step committed before the next could influence it):** success criteria; the new rule, chosen on training and validation engines only; the FD002/FD004 models and settings; then the test replays.

## The rule (pre-registered, v2)

- **Wear-adjusted residuals:** each reading is compared with what that sensor should read for an engine of that age and predicted remaining life (spline models on training engines with out-of-fold predictions), divided by the expected spread: z = (reading - expected) / spread.
- **Drift:** per-engine mean z over the last 3 shifts vs the training engines' windows, KS, Holm over 14 sensors. A sensor triggers retraining if drifted (alpha 0.05) in 2 of the last 3 runs, or once with p < 1e-10 (reason: *sensor fault suspected, check the sensor before retraining*).
- **Health:** squared error of the last 20 labelled engines vs the error expected for engines of the same life (limit 2.9x), and a binomial test of their lower-bound misses against the validation rate (alpha 0.01).
- **Calibration fleets:** cross-fitted: models on half A of the training engines, fleet = half B + validation (60 engines); 15 replicates per half and mode; cut-off 25%-95% of life; staggered offsets 0-150; injections in 3 staggered replicates per half. On the same fleets the old Phase 7 test raised up to 40.1% false alarms; the new rule at most 1.4% (budget 2%).

## Why FD004 failed C1

**A defect, found and fixed, that was not the cause.** The spread model fits the mean absolute residual directly and can go to zero or below in sparse corners; the code then divides by a floor of 1e-6. On FD004's oldest test engines this produced standardised residuals in the millions:

| Dataset | Readings with abs(z) > 20, v2 | Largest abs(z), v2 | Smallest predicted spread, v2 | Same three, v2.1 (log-scale spread) |
| --- | --- | --- | --- | --- |
| FD001 | 0 | 5 | 0.02 | 0, 5.9, 0.01 |
| FD003 | 2 | 70 | 0.02 | 0, 11.8, 0.02 |
| FD002 | 0 | 5 | 0.30 | 0, 5.1, 0.30 |
| FD004 | 975 | 1,906,941 | -0.31 | 0, 16.8, 0.12 |

v2.1 models log(abs residual), so the spread is positive by construction; re-chosen with the same validation-only procedure it kept every decision parameter (alpha 0.05, 2 of 3, strong 1e-10, error limit 2.9, miss alpha 0.01). It is **post hoc**: every test set had been seen, so none of its test results is a confirmation. Re-scored with v2.1, FD004 still fails:

| Clean-run flags | v2 (pre-registered) | v2.1 (post hoc) |
| --- | --- | --- |
| FD002 synchronized | 0/554 = 0.0% | 0/554 = 0.0% |
| FD002 staggered | 6/667 = 0.9% | 5/667 = 0.7% |
| FD004 synchronized | 108/554 = 19.5% | 104/554 = 18.8% |
| FD004 staggered | 93/667 = 13.9% | 75/667 = 11.2% |

**The likely cause: two fault modes.** FD004's flags are persistent drift in several sensors at once, late in the replay (shifts 172-342, synchronized), when few engines are left. Their mean residual pattern correlates +0.77 and -0.82 with the end-of-life residual signatures of the two groups of FD004 training engines split by the direction of s20 (a proxy for the two fault modes, which NASA does not label). The expected-level model averages the two modes, so a late group dominated by one mode's degradation pattern looks drifted. This is consistent with the data but not proven: the crude mode proxy does not show the survivors dominated by one mode. A mode-aware expected level is the next step; it would need data nobody has seen yet to confirm it.

## Closed loop: when the model's own decisions hide the labels

In shadow mode every engine eventually fails and gets a label. When the recommended services are carried out (`--closed-loop`, FD002/FD004 synchronized), a serviced engine never fails, so its label never arrives.

| | FD002 | FD004 |
| --- | --- | --- |
| Engines whose failure label arrives | 37 of 259 | 5 of 248 |
| Lower-bound miss rate from labels only | 24.3% | 100.0% |
| Bounds using every engine (censored included) | 3.5% - 83.4% | 2.0% - 92.3% |
| True miss rate (NASA truth; a plant would not know it) | 3.9% | 4.4% |

The engines that still fail are mostly the model's misses, so a monitor that only learns from failures sees a broken model where there is none (the FD002 closed-loop replay set the miss-rate flag in 369 of 554 runs). A serviced engine survived until its service, which rules out a miss when that time already exceeds the forecast's lower bound; the resulting bounds contain the truth but are too wide to act on, because most services come before the lower bound has elapsed. A real deployment needs another label source: inspection findings recorded at service, or a small control group kept on a fixed service policy.

## Limitations

- C1 failed on FD004 with the pre-registered rule, and the post-hoc fix does not change that; the cause is likely the fault-mode mixture, not proven.
- All four NASA datasets are now used; no unseen data is left to confirm a further change.
- Calibration fleets have 60 engines (test fleets 100-260); late-replay windows with 15-45 engines are where the false alarms concentrate.
- Fleet-wide faults only: one engine's broken sensor is a per-engine check, not a fleet drift test.
- The plant clock, services and labels are simulated from NASA's data.

## Reproduce

Each scenario is one command, e.g. `python -m pipeline.flow --replay-all --monitor v2 --fleet staggered --datasets FD002 FD004 --schema ops7b_fresh_staggered --out-dir pipeline/phase7b/fresh_staggered` (`--monitor v2.1` for the post-hoc fix, `--closed-loop` for the closed loop). Health, drift, alert and run tables of every scenario are committed; of the forecast tables (about 15 MB each) only the three the verifier reads are committed, gzip-compressed. Then `python -m pipeline.check_phase7b` (with `--closed-loop` and `--diagnosis`), `python -m pipeline.fault_suite FD002 FD004` (and `--equivalence`), `python -m pipeline.report_phase7b`, `python -m pipeline.verify_phase7b`.
