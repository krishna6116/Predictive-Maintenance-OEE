# Orchestration and monitoring (Phase 7)

Generated by `python -m pipeline.report_phase7` from `pipeline/results_phase7.json`, `pipeline/phase7_checks.json` and `pipeline/monitoring_rule.json`; do not edit by hand. Independent checks: `python -m pipeline.verify_phase7`. Walkthrough: `notebooks/07_monitoring.ipynb`.

> **What is real and what is simulated.** Forecasts are real outputs of the published LSTM. The plant clock is simulated: every NASA test engine starts at cycle 1 on shift 1, one shift is one 8-hour cycle, and an engine's failure enters the plant's log at its true failure cycle (last NASA reading + NASA's true remaining life). Work orders are recommendations (shadow mode): the recorded NASA data keeps flowing after them.

## The shift flow

One Prefect flow run per shift (`pipeline/flow.py`), for each of FD001, FD003: ingest -> validate -> load -> features -> predict_and_store -> alerts -> schedule -> model health -> drift -> retraining flag. Steps that touch the database or files retry 3 times, 10 s apart. Run IDs are fixed per shift (`FD001-test-s0137`), so re-running a shift replaces its rows, and a failed shift is resumed by the next run. The replay uses its own Postgres schema (`ops`).

- **Model:** the published seed-0 LSTM with rule-E intervals. Before predicting, the flow proves the model reproduces the published last-cycle predictions and all 100 MC-dropout passes exactly (`maintenance.forecasts.published_model`). Predictions run in fixed batches of 100 windows, which makes them bit-identical to the published ones.
- **Decisions:** Phase 6's alert rule and CP-SAT planning step (`maintenance.simulate.plan_day`), at the start of each day (every 2 shifts). The database allows one flow work order per engine.
- **Commands:** `prefect server start` (dashboard http://127.0.0.1:4200), `prefect config set PREFECT_API_URL=http://127.0.0.1:4200/api`, then `python -m pipeline.flow --once`, `--serve` (a shift every 600 s; `--interval` overrides), `--replay-all`, `--reset` (the replay schema only).

## Rules fixed before the test replay (validation engines only)

`pipeline/calibrate_monitoring.py` chose these on the 20 validation and 80 training engines of each dataset and committed `pipeline/monitoring_rule.json` before the flow replayed any test data.

| Rule | Choice | Evidence on validation |
| --- | --- | --- |
| Drift test | per-engine means of the last 3 shifts vs age-matched training engines, KS, Holm over 14 sensors; at least 15 engines a side | reading-level KS rejected: false alarms on clean validation streams 9.9% at alpha 0.05 and still 2.6% at 0.0005, all in FD003 runs where about 19 engines each gave 3 near-identical readings |
| Significance | alpha 0.01 | false alarms per clean run: 0.05: 1.7%, 0.01: 0.3%, 0.005: 0.0%, 0.001: 0.0%, 0.0005: 0.0%; chosen 0.28% over 363 runs (budget 2%) |
| RMSE rule | rolling RMSE of the last 20 labelled engines > 1.45 x validation RMSE (FD001 11.02, FD003 11.90) | 1.30 x would raise false alarms in FD001 6.6%, FD003 7.2% of clean windows; chosen: FD001 1.4%, FD003 1.4% |
| Miss-rate rule | lower-bound miss rate of the last 20 labelled engines > 20% | leave-one-engine-out miss rate FD001 5.1%, FD003 6.6%; false alarms FD001 0.5%, FD003 0.8% |
| Retraining flag | any of: >= 1 drifted sensor, the RMSE rule, the miss-rate rule (health rules need 20 labelled engines) | combined false-alarm estimate 2.52% per run |

## Can the drift test see a shift?

Detection rate when one sensor is shifted, averaged over sensors (weakest sensor in brackets). Validation streams have 20 engines; test windows about 100. *Persistent* = the whole window is shifted; *newest shift* = only the latest readings.

| Shift | Validation, persistent | Validation, newest shift | Test windows, newest shift |
| --- | --- | --- | --- |
| +1% | 99% (s21 92%) | 66% (s4 9%) | 79% (s4 38%) |
| +2% | 100% (s2 100%) | 95% (s15 83%) | 96% (s4 76%) |
| +5% | 100% (s2 100%) | 100% (s15 100%) | 100% (s2 100%) |
| +0.5 sd | 26% (s21 2%) | 0% (s2 0%) | 4% (s2 0%) |
| +1 sd | 89% (s20 74%) | 8% (s21 0%) | 27% (s2 2%) |

Percent shifts are large for these sensors (+1% is many standard deviations), so most of them also leave the sensor's allowed range and are quarantined by the validator. Drift is tested on everything received, so it still sees them; shifts of a fraction of a standard deviation pass validation and are the harder case.

## Did the pre-registered rule hold up on clean test data?

| Target | Validation (when chosen) | Clean test replay | Met? |
| --- | --- | --- | --- |
| Drift false alarms <= 5% of runs | 0.28% | 11.6% (51 of 438 tested runs; FD001 3.2%, FD003 18.1%) | **no** |
| Retraining flag on clean data <= 5% of runs | estimate 2.5% | 6.2% (60 of 968 runs) | **no** |

Nothing was injected in the replay, so every flag above is a false alarm. The limits were not moved after seeing them (that would tune the rule on the test engines). Both causes were traced:

**1. The drift reference matches age, not wear.** NASA cut each test engine off at a different point, so late in the replay the engines still reporting are a selected group that is healthier than the training engines of the same age (which run to failure). In the flagged windows:

| Dataset | Runs | Median remaining life: test engines | Median remaining life: reference | Within 50 cycles of failure: test | Within 50: reference |
| --- | --- | --- | --- | --- | --- |
| FD001 | 6 flagged | 62 | 43 | 33% | 54% |
| FD001 | 183 not flagged | 120 | 107 | 13% | 20% |
| FD003 | 45 flagged | 104 | 66 | 5% | 41% |
| FD003 | 204 not flagged | 138 | 120 | 6% | 15% |

Every sensor that 'drifted' (s4 30x, s8 23x, s13 21x, s3 18x, s11 18x, s17 16x, s2 15x) is among the 7 sensors most correlated with remaining life (s11, s4, s17, s2, s3, s8, s13); the least wear-related sensors never drifted. The test detected a difference in wear, not a sensor fault. Validation engines run to failure without this cut-off, which is why the calibration did not see it.

**2. The first labels come from the shortest-lived engines.** Labels arrive in order of failure, so the first window of 20 holds the engines that failed first, and the model is less accurate on them:

| Dataset | First 20 labelled: median life, RMSE | Other 80: median life, RMSE |
| --- | --- | --- |
| FD001 | 153 cycles, 19.00 | 210 cycles, 11.44 |
| FD003 | 166 cycles, 18.78 | 238 cycles, 10.58 |

**What would fix it** (not done here, because it would need data not yet seen to confirm): a drift reference matched on wear stage as well as age, and an RMSE reference that matches the life of the engines labelled so far, both chosen on validation engines cut off the way NASA cut the test engines, then confirmed on a fresh dataset (FD002 or FD004), the way Phase 5b confirmed the model on FD003.

## Limitations

- One shift is one cycle and all engines start together; a real fleet is staggered.
- Labels come late: an engine is scored only after it fails, so the health rules see nothing until the first failures and only ever see the engines that fail first early on.
- In shadow mode recommended services do not stop the data. If they were executed, most engines would be serviced before failing and their labels would never arrive (censoring), which a real deployment has to plan for.
- Validation streams have 20 engines, so the false-alarm and power estimates are coarse; test windows have ~100.
- The exact model check runs only on the operating system that published the model; CI on Linux replays the committed predictions instead.
