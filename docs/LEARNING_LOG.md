## 2026-10-18: Phase 4, baselines

- Results (test RMSE): fleet average 41.94, Ridge raw 20.59, Ridge 168 features 16.28, XGBoost 168 features 15.38 (12.4-18.2; 5-seed spread 0.20).
- Features are the real win (Ridge -4.3). XGBoost vs Ridge is a tie overall, but near failure XGBoost's MAE is 4.8 vs 13.3 and Ridge runs late (+9.3); checked at cut-offs 25-75 so it is not cherry-picked.

## 2026-10-18: Phase 4 reproducibility (CI on Linux)
- CI failed on one check: re-training XGBoost on Linux gave predictions up to 6.8 cycles away from the ones published from Windows. Pinning library versions (requirements-lock.txt) did not change it, which ruled out versions.
- Two causes. (1) Thread count: on the same laptop, 1 vs 4 threads moved predictions by up to 10 cycles. (2) Operating system: row/column subsampling draws random numbers through the C++ standard library, which differs between Windows and Linux, so the same seed gives different trees.
- Fixes: XGBoost now runs on one fixed thread (`n_jobs=1`), and results record the OS, XGBoost version and thread count. The verifier demands identical predictions on the producing OS; on any other OS it re-trains all 5 seeds and requires the 5-seed mean test RMSE within 0.6 of the published one. 0.6 is over 5 standard deviations of chance (seed sd 0.17), yet every wrong feature set in the ablations (gaps +0.7 to +2.1) would fail it.
- Re-ran Phase 4 with one thread: the 4 non-XGBoost models are identical to the digit; XGBoost test RMSE 15.38 -> 15.08 (inside the old 5-seed range 14.87-15.38), PHM08 588 -> 565, near-failure MAE 4.8 -> 4.4. Every conclusion and the validation-based model choice are unchanged.
- Notebook findings and the why-table are now generated from the results, with each claim asserted (a false claim stops the build). The verifier also checks the README's headline numbers. CI runner pinned to ubuntu-24.04 (ubuntu-latest moves to Ubuntu 26 on 2026-10-19). Added tests/test_baselines.py.
- Verification 23/23 in both modes (exact, and simulated other-OS); Phase 3 25/25; 38 tests pass.
- Lesson: "same seed" only means "same result" with the same threads, library and OS. Record the environment with every result.

## 2026-10-18: Phase 5, deep learning (LSTM and 1D-CNN)
- Inputs: causal windows of the 14 scaled sensors, left-padded with copies of each engine's first reading; tested for no leakage (rewriting an engine's future leaves its earlier windows unchanged) and rebuilt value by value by an independent plain-Python builder.
- Search on validation only (seed 0): window 20/30/40 x hidden 32/64, then dropout 0.1-0.3 x learning rate 1e-3/3e-3; early stopping (patience 8). Final: LSTM window 40, hidden 64, dropout 0.1, lr 0.003; CNN window 40, hidden 64, dropout 0.1, lr 0.001. LSTM published as the deep model (5-seed validation 11.08 vs 12.23). 5 seeds each, refit on 100 engines for each seed's validated epochs; full run 74 min on one CPU thread.
- Result: LSTM test RMSE 13.30 (10.5-16.1), PHM08 441, near-failure MAE 3.1, seeds 13.53 +/- 0.34. On validation it beats XGBoost clearly (test-like -3.47, near failure -1.99), but on the 100 test engines the RMSE gap is -1.78 (-4.54 to +0.57), Holm p 1.0. By the pre-set rule, **XGBoost stays the published model**. LSTM vs CNN: tie. 168-feature windows: no gain.
- MC dropout (100 passes): raw 90% intervals cover only 75.7% on validation. Scale k = 2.71 learned on validation -> 89.6% leave-engines-out; test coverage 65% raw -> 82% calibrated (88% near failure). Test coverage stays below nominal: honest gap, reported, not tuned on test.
- Cross-OS verification: the statistical band (1.49 RMSE) misses small bugs (half epochs, s4 missing, zero padding). So exact input checks (window rebuild) and an epoch-count check, both OS-independent, back it up; `models/tolerance_phase5.py` shows every deliberate bug is caught by at least one check.

(2) A second Claude session edited the tolerance study, verifier, report, notebook and README mid-phase; I reviewed its changes, kept its window-rebuild design and re-ran the study. (3) The verifier found that pandas' default CSV parser changes the last binary digit of some floats (1.4e-14); all CSVs are now read with `float_precision="round_trip"`, and the Phase 4 XGBoost/Ridge columns copied into the Phase 5 files were restored to Phase 4's exact values (no number changes at any printed digit).
