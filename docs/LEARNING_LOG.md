## 2026-10-18: Phase 4 reproducibility (CI on Linux)
- CI failed on one check: re-training XGBoost on Linux gave predictions up to 6.8 cycles away from the ones published from Windows. Pinning library versions (requirements-lock.txt) did not change it, which ruled out versions.
- Two causes. (1) Thread count: on the same laptop, 1 vs 4 threads moved predictions by up to 10 cycles. (2) Operating system: row/column subsampling draws random numbers through the C++ standard library, which differs between Windows and Linux, so the same seed gives different trees.
- Fixes: XGBoost now runs on one fixed thread (`n_jobs=1`), and results record the OS, XGBoost version and thread count. The verifier demands identical predictions on the producing OS; on any other OS it re-trains all 5 seeds and requires the 5-seed mean test RMSE within 0.6 of the published one. 0.6 is over 5 standard deviations of chance (seed sd 0.17), yet every wrong feature set in the ablations (gaps +0.7 to +2.1) would fail it.
- Re-ran Phase 4 with one thread: the 4 non-XGBoost models are identical to the digit; XGBoost test RMSE 15.38 -> 15.08 (inside the old 5-seed range 14.87-15.38), PHM08 588 -> 565, near-failure MAE 4.8 -> 4.4. Every conclusion and the validation-based model choice are unchanged.
- Notebook findings and the why-table are now generated from the results, with each claim asserted (a false claim stops the build). The verifier also checks the README's headline numbers. CI runner pinned to ubuntu-24.04 (ubuntu-latest moves to Ubuntu 26 on 2026-10-19). Added tests/test_baselines.py.
- Verification 23/23 in both modes (exact, and simulated other-OS); Phase 3 25/25; 38 tests pass.
- Lesson: "same seed" only means "same result" with the same threads, library and OS. Record the environment with every result.

## 2026-10-18: Phase 5, deep learning (LSTM and 1D-CNN)

Final: LSTM window 40, hidden 64, dropout 0.1, lr 0.003; CNN window 40, hidden 64, dropout 0.1, lr 0.001. On validation it beats XGBoost clearly (test-like -3.47, near failure -1.99), but on the 100 test engines the RMSE gap is -1.78 (-4.54 to +0.57), Holm p 1.0. ## 2026-10-23/24: Phase 7, orchestration and monitoring (Prefect)
- Pre-registration first (commit cce5187, before any test replay): rules chosen on validation and training engines only. Reading-level KS was rejected: on clean validation streams it raised false alarms in 9.9% of runs at alpha 0.05 and still 2.6% at 0.0005, because 3 near-identical readings per engine were treated as independent evidence. Per-engine KS + Holm: alpha 0.01 -> 0.28%. The brief's 30% RMSE rule would raise ~7% false alarms on 20-engine windows; 1.45x gives ~1.4%. Miss-rate limit > 20%. Combined estimate 2.5% per run.
- Flow: one Prefect run per 8-hour shift (= one cycle), 10 tasks per dataset, retries on DB/file steps, fixed run IDs, resume after failure, shadow-mode work orders, replay in its own Postgres schema (ops). Phase 6's planning step is shared, not copied; Phase 6 outputs stayed identical.
- Published model only: weights are cached locally (git-ignored) and the model must reproduce the published predictions and all MC passes exactly before use. Finding: LSTM outputs differ in the 5th decimal with batch size (CPU matrix kernels); predicting in fixed batches of 100 makes them bit-identical to the published ones, so the final monitored RMSE equals the published 13.30 / 12.66 exactly.
- Bugs found and fixed: (1) SQLAlchemy 2.1.5 broke the Prefect server's scheduler (.serve() created no runs); pinned 2.0.55, all earlier tests/verifiers still pass. (2) fact_alert's foreign key assumed the alert and its forecast share a run; added forecast_run_id (migration keeps Phase 6 rows). (3) all-NULL health metrics were written as text. (4) a test-data gap in replay mode was not marked invalid. (5) found by the verifier: per-engine sensor means are often exactly tied, and the order of additions decided how ties were ordered, moving KS statistics by up to 0.03. Fixed by rounding means to 9 decimals; the recalibration on validation picks the same rule (monitoring_rule_recheck.json); the full replay was re-run.
- Results (484 shifts, 968 runs, 29,692 forecasts, 198 work orders): the guide's +5% check passes (all 100 shifted readings quarantined, drift still flags the sensor, retraining flag set; clean runs before it set nothing). +1 sd in one shift is caught by drift (passes validation).
- Honest failure: on clean test data the drift test fired in 11.6% of runs (FD001 3.2%, FD003 18.1%) against a 5% target, and the retraining flag in 6.2% of runs. Traced, not tuned: the reference matches age but not wear (late test engines are healthier than training engines of the same age; every 'drifted' sensor is one of the 7 most wear-related), and the first labels come from the shortest-lived engines (RMSE 19.0 vs 11.4), which tripped the RMSE rule on FD001. A fix must be chosen on validation and confirmed on fresh data (FD002/FD004).
- Verification: pipeline/verify_phase7.py 25/25 (independent KS from raw files, health, flags, orders, exact model re-run on Windows), 26/26 with a fresh 150-shift replay (used in CI on Linux); four planted bugs all caught. 100 tests pass; Phase 3-6 verifiers still pass; notebook 0 errors.
- Lesson: a rule calibrated on run-to-failure validation engines can still fail on truncated test engines; and "exact" checks also need exact ties.
